# Pokédex for Kids 專案憲章

## 核心原則

### 一、最小可行產品優先（MVP First）

**每個功能都必須從最小可行版本開始**。避免過度設計，專注於交付核心價值。

**核心規則**：
- 必須先定義功能的最小核心範圍，完成後再考慮擴充
- 禁止在首次實作時加入「未來可能需要」的功能
- 每個使用者故事必須可獨立測試和部署
- 使用優先級（P1, P2, P3...）來組織功能，P1 就是 MVP

**理由**：快速驗證想法，避免浪費資源在不必要的功能上。小步快跑，持續交付價值。

### 二、測試先行（Test-First）（不可妥協）

**所有程式碼必須採用測試驅動開發（TDD）**。沒有通過的測試，就沒有實作。

**核心規則**：
- 必須先撰寫測試，確認測試失敗後才開始實作
- 嚴格遵守紅燈→綠燈→重構循環
- 每個使用者故事必須有對應的整合測試
- 測試覆蓋率不是目標，可測試性才是重點

**測試層級**：
- **單元測試**（Unit Tests）：驗證單一函式或元件的行為
- **整合測試**（Integration Tests）：驗證多個元件協同工作
- **合約測試**（Contract Tests）：驗證 API 端點或元件介面

**理由**：測試先行確保程式碼品質，減少 bug，提升重構信心。可測試的程式碼自然是設計良好的程式碼。

### 三、型別安全與 TypeScript 優先

**必須充分利用 TypeScript 的型別系統來保證程式碼正確性**。

**核心規則**：
- 禁止使用 `any` 型別，除非有明確且記錄的理由
- 所有公開 API 必須有完整的型別定義
- 使用 TypeScript 的嚴格模式（strict mode）
- 優先使用型別推論，避免冗餘的型別標註

**理由**：型別系統在編譯時捕捉錯誤，減少執行時錯誤，提升開發效率和程式碼可維護性。

### 四、元件化與可重用性

**每個 UI 元件必須是獨立、可重用、可測試的單元**。

**核心規則**：
- 元件必須是純粹的或明確管理副作用
- 每個元件必須有明確的職責，不超過 200 行（不含測試）
- 元件必須通過 props 接收資料，避免直接存取全域狀態
- 共用元件必須放在 `components/` 目錄下

**理由**：可重用的元件減少重複程式碼，提升開發速度。獨立的元件更容易測試和維護。

### 五、效能與使用者體驗

**必須確保應用程式快速且響應流暢**。

**核心規則**：
- 首次內容繪製（FCP）必須在 1.5 秒內
- 最大內容繪製（LCP）必須在 2.5 秒內
- 互動時間（TTI）必須在 3.5 秒內
- 使用 Next.js 的 Image 元件優化圖片載入
- 實作適當的載入狀態和錯誤處理

**理由**：良好的效能直接影響使用者體驗，特別是針對兒童使用者，需要即時的回饋和流暢的互動。

### 六、可存取性（Accessibility）

**應用程式必須符合 WCAG 2.1 AA 級標準**。

**核心規則**：
- 所有互動元素必須可透過鍵盤操作
- 必須提供適當的 ARIA 標籤
- 色彩對比度必須符合 AA 級標準（4.5:1）
- 所有圖片必須有替代文字

**理由**：確保所有兒童，包括有特殊需求的兒童，都能使用應用程式。

### 七、正體中文優先

**所有文件、註解、提交訊息、使用者介面文字必須使用正體中文**。

**核心規則**：
- 程式碼註解必須使用正體中文
- Git 提交訊息必須使用正體中文
- 文件（README、規格、計畫）必須使用正體中文
- 使用者介面文字必須使用正體中文
- 變數和函式名稱使用英文（遵循慣例）

**例外**：第三方套件的文件或技術術語可保留英文。

**理由**：確保團隊成員能用母語溝通，減少誤解，提升協作效率。

## 技術標準

### 程式碼品質

- **Linting**：必須通過 ESLint 檢查，無警告
- **格式化**：使用一致的程式碼格式（建議使用 Prettier）
- **程式碼審查**：所有 PR 必須經過至少一位團隊成員審查
- **提交規範**：使用語義化提交訊息（feat:, fix:, docs:, refactor:, test:）

### 安全性

- **輸入驗證**：所有使用者輸入必須驗證和消毒
- **XSS 防護**：使用 React 的內建保護機制，避免使用 `dangerouslySetInnerHTML`
- **依賴管理**：定期更新依賴套件，修補安全漏洞
- **環境變數**：敏感資訊必須存放在環境變數中，不得提交到版本控制

### 文件要求

- **README**：必須包含專案說明、安裝步驟、執行方式
- **API 文件**：公開 API 必須有清晰的文件
- **元件文件**：複雜元件必須有使用範例
- **變更日誌**：重大變更必須記錄在 CHANGELOG 中

## 開發工作流程

### 功能開發流程

1. **規格定義**：使用 `/speckit.specify` 建立功能規格
2. **計畫制定**：使用 `/speckit.plan` 制定實作計畫
3. **任務分解**：使用 `/speckit.tasks` 產生可執行任務
4. **測試先行**：撰寫測試並確認失敗
5. **實作功能**：實作最小可行版本
6. **通過測試**：確保所有測試通過
7. **程式碼審查**：提交 PR 並接受審查
8. **部署驗證**：在測試環境驗證功能

### 分支策略

- **main**：主分支，永遠保持可部署狀態
- **feature/**：功能分支，從 main 分出
- **fix/**：修復分支，用於緊急修復

### 提交要求

- 提交訊息必須清晰描述變更內容
- 每次提交必須是原子性的（一個邏輯變更）
- 提交前必須確保測試通過
- 提交前必須執行 lint 檢查

## 治理規範

### 憲章地位

本憲章凌駕於所有其他開發實踐之上。所有 PR 和程式碼審查都必須驗證是否符合憲章要求。

### 修訂程序

1. **提議變更**：團隊成員提出修訂建議，說明理由和影響範圍
2. **討論評估**：團隊討論變更的必要性和影響
3. **版本更新**：根據變更類型更新版本號：
   - **主版本（MAJOR）**：移除或重新定義核心原則（向後不相容）
   - **次版本（MINOR）**：新增原則或大幅擴充指引
   - **修訂版本（PATCH）**：澄清、措辭調整、錯字修正
4. **文件同步**：更新所有相關模板和文件
5. **遷移計畫**：如有需要，制定現有程式碼的遷移計畫

### 合規審查

- 每個 PR 必須在描述中說明如何符合憲章要求
- 定期（每季）審查程式碼庫的合規狀況
- 發現違規時必須記錄並制定改善計畫

### 例外處理

如需偏離憲章原則，必須：
1. 在 PR 或規格文件中明確說明理由
2. 評估更簡單的替代方案並說明為何不可行
3. 獲得至少兩位團隊成員的批准
4. 記錄技術債務並制定未來的改善計畫
